# Витрина бронирования проката

Frontend-витрина проката туристического снаряжения на Next.js.
Граница проекта — поиск по каталогу, корзина и личная история одного клиента.

## Стек

- Next.js 16 (App Router), React 19, TypeScript
- SCSS-модули
- zod — валидация на границах (URL, формы, тело запросов, localStorage)

## Запуск

```bash
npm install
npm run dev
```

Демо-доступ: `samir@mail.ru` / пароль указан на странице входа.

## Мок-API

API реализован внутри проекта на Route Handlers
(`src/app/api/**`), а данные лежат в `src/server/mock/`.

Это дало то, чего фиксированная песочница дать не может: возможность вызвать
любой сценарий ошибки по требованию — 409, 401, сбой оплаты, временный сбой
каталога. Именно они и составляют суть задания.

Граница между клиентом и API осталась настоящей: обмен идёт по HTTP, клиент
никогда не импортирует моковые данные напрямую.

## Серверное и клиентское

Основной принцип: **на сервере — данные и разметка, на клиенте — только то,
что требует взаимодействия с пользователем.**

### Серверные компоненты

| Что | Почему |
|---|---|
| Каталог (`app/page.tsx`) | HTML с товарами приходит готовым — индексируемая основа выдачи |
| Карточка товара (`app/equipment/[id]`) | то же плюс `notFound()` с честным 404 |
| Пагинация | это набор `<Link>`, интерактивность не нужна; ссылки индексируются и открываются в новой вкладке |
| Карточка в выдаче | только отображение |
| Рекомендации | второстепенный блок, грузится потоком через `<Suspense>` |
| История броней | защищённая страница: проверка сессии и `redirect` происходят до рендера, неавторизованный не получает HTML с данными |

Ни один из этих компонентов не попадает в браузерный бандл.

### Клиентские компоненты

| Что | Почему |
|---|---|
| Фильтры каталога | `onChange`, `useTransition` для индикатора загрузки |
| Выбор периода | интерактивная панель с состоянием открытия |
| Корзина и её части | состояние в контексте, обработчики |
| Формы (вход, контакты) | ввод и валидация по ходу |
| Границы ошибок (`error.tsx`, `SafeBlock`) | механизм перехвата построен на состоянии React |

### Где проходит граница

Граница определяется **импортами, а не деревом компонентов**. Клиентским
становится файл с `"use client"` и всё, что он импортирует. То, что ему передали
через `children`, остаётся серверным.

Это использовано в двух местах:

- `SafeBlock` — клиентская обёртка `ErrorBoundary` + `Suspense`, внутрь которой
  страница передаёт серверный блок рекомендаций
- `CartProvider` и `AuthProvider` — клиентские провайдеры вокруг серверных страниц

### Что не уезжает на клиент

Справочник категорий вынесен в отдельный маленький модуль (`shared/labels.ts`),
чтобы фильтры не тянули за собой моковую базу снаряжения. Всё, что читает куки
и хранилища, лежит в `src/server/` — оттуда клиент не импортирует.

## Состояние: где что живёт

### Фильтры и пагинация — в URL

Категория, цены, сортировка, номер страницы и даты кодируются в `searchParams`.
Выдачей можно поделиться, кнопка «назад» работает сама собой, а при заходе по
прямой ссылке состояние восстанавливается без дополнительного кода: значения
элементов управления читаются из URL, а не из `useState`.

Клиент не запрашивает данные сам — он меняет адрес, а Next перезапускает
серверный рендер страницы.

### Корзина — контекст + localStorage

Корзина переживает переходы между страницами и перезагрузку вкладки, в URL её
не закодировать. Состояние оформлено как явная модель:

- `shared/cart/model.ts` — типы, `calculateTotals`, `validateDates`. Ни одного
  импорта из React, поэтому те же функции используются и в route handlers на
  сервере
- `shared/cart/reducer.ts` — действия `add`, `remove`, `setQty`, `setDates`,
  `toggleExtra`, `clear`
- `shared/cart/CartProvider.tsx` — связь с React

Итог не хранится в состоянии: `calculateTotals` вызывается при каждом рендере.
Поэтому сумма не может разойтись с содержимым корзины — пересчёт после любого
действия даёт один результат по определению.

Восстановление из `localStorage` сделано **ленивой инициализацией**
(`useReducer(reducer, INITIAL, init)`), а не эффектом. С двумя эффектами —
«загрузить» и «сохранить» — возникала гонка: эффект сохранения успевал записать
пустую корзину до того, как отрабатывало восстановление. Ленивый init убирает
саму ситуацию: состояние верно с первого рендера, сохранять поверх нечего.

Цена решения — расхождение при гидратации: сервер не знает `localStorage`.
Лечится флагом `mounted` там, где рисуется клиентское состояние (счётчик в шапке,
корзина).

### Даты — в корзине и в URL одновременно

Период нужен в двух качествах: как свойство заказа (он общий для всей корзины,
доступен на всех страницах) и как параметр фильтрации (сервер должен знать,
что показывать, ссылка должна работать).

Источник истины — корзина. URL получает копию:

- **корзина → URL**: при изменении периода, если пользователь на каталоге или
  карточке, оба ключа ставятся одним `URLSearchParams` и уходят одним `push`
- **URL → корзина**: один раз при заходе на каталог (`CatalogDatesSync`).
  Если в адресе есть даты — они главнее, это присланная ссылка. Если нет, а в
  корзине есть — подставляются в адрес через `replace`

Копирование в момент изменения, а не слежка через `useEffect`, исключает цикл
«корзина → URL → корзина».

## Слой запросов

`src/shared/api/` — единственное место, где приложение знает про HTTP.
Компоненты вызывают функции и ловят `ApiError` со статусом.

Различаются четыре ситуации:

| Ситуация | Как выражена |
|---|---|
| Транспортный сбой | `fetch` бросает сам — ошибка не `instanceof ApiError` |
| Ошибка валидации | `ApiError` со статусом 400 |
| Истёкшая сессия | `ApiError` со статусом 401 |
| Конфликт данных | `ApiError` со статусом 409, в `data` — список конфликтных позиций |

Отдельно: «не найдено» не является ошибкой. `getEquipmentById` возвращает `null`
при 404, `fetchMe` — при 401. Это нормальные ответы, а не сбои.

Все данные, приходящие извне, проходят через zod: параметры URL, тело запросов,
содержимое `localStorage`. Аннотация типа после `res.json()` ничего не
проверяет — схема проверяет.

## Пути восстановления

Каждая ошибка ведёт себя по-своему.

**409 — конфликт наличия.** Сервер возвращает список позиций с запрошенным и
доступным количеством. Интерфейс подсвечивает именно их, остальная корзина цела,
появляется кнопка «Пересчитать заказ» — она приводит количества к доступным.

**401 — нет сессии.** Сбрасывается состояние в `AuthProvider` (иначе контекст
считает, что пользователь вошёл, и страница входа отправляет его обратно), затем
переход на `/login?from=/cart` с возвратом после входа.

**Ошибка оплаты (502).** Корзина не очищается, ключ идемпотентности не
расходуется, действие можно повторить. Для проверки на странице корзины есть
переключатель «Имитировать сбой оплаты».

**Транспортный сбой.** Отдельное сообщение про соединение — техническое
`Failed to fetch` пользователю ничего не говорит.

**Состояния каталога.** Различаются первичная загрузка (`loading.tsx`),
обновление при смене фильтров (`useTransition`), пустая выдача (объяснение и
сброс фильтров), 404 карточки (`notFound.tsx`), временный сбой API (`error.tsx`
с кнопкой повтора).

Ошибка второстепенного блока изолирована: рекомендации обёрнуты в `SafeBlock`
(`ErrorBoundary` снаружи, `Suspense` внутри). Их падение не задевает основное
содержимое, повтор — через `router.refresh()`.

**Некорректные параметры URL** не роняют страницу. `parseCatalogParams` проверяет
их схемой, сломанные поля заменяются значениями по умолчанию, а список подмен
возвращается вместе с данными и показывается плашкой: «Номер страницы был
некорректным — показана первая страница».

## Идемпотентность

Повторное подтверждение не должно создавать вторую бронь — при двойном клике,
обновлении страницы или повторе после потери связи.

Клиент присылает заголовок `Idempotency-Key`, сервер хранит обработанные ключи
вместе с выданным результатом и на знакомый ключ возвращает тот же номер брони,
ничего не создавая.

Ключ состоит из двух частей: случайного UUID и **отпечатка корзины** —
стабильной строки из позиций, количеств, дат и услуг. Обе нужны:

- без UUID два одинаковых заказа в разное время считались бы дублем
- без отпечатка изменение корзины после неудачной попытки не учитывалось бы:
  повтор вернул бы старый результат, а правки потерялись

Пара «UUID + отпечаток» хранится в `localStorage`, чтобы пережить перезагрузку.
При отправке отпечаток пересчитывается: совпал — берётся сохранённый ключ,
не совпал — создаётся новый. После успеха ключ удаляется.

## Принятые решения

**Дни аренды** считаются как число суток между датами: с 14 по 17 сентября —
3 дня. День возврата не оплачивается и не считается занятым, поэтому проверка
пересечения периодов работает на полуинтервале `[from, to)`.

**Залог входит в «К оплате»**, но показан отдельной строкой с пометкой
«возвратный» — так сумма к оплате совпадает с тем, что человек реально отдаёт
в пункте выдачи. Разбивка по строкам: аренда, дополнительные услуги, залог.

**Бронь хранит снимок**, а не ссылки: названия, цены за день и залоги на момент
заказа плюс полный расчёт. Если прокат изменит цену, старая бронь в истории
покажет то, за что было заплачено.

**Цены всегда считает сервер.** Клиент присылает только идентификаторы и
количества — иначе можно было бы подделать сумму. При этом обе стороны
используют одну функцию `calculateTotals`, поэтому расчёты гарантированно
совпадают.

**Доступность считается одной функцией** `freeQty` — склад минус брони,
пересекающиеся по датам, с учётом заблокированных дней. Её используют и фильтр
каталога, и бейджи на карточках, и проверка при создании брони, поэтому они не
могут разойтись.

**Значения в URL — коды, не подписи.** В адресе `category=tents`, человеческое
«Палатки» подставляется при отрисовке через справочник. Данные не зависят от
языка интерфейса.
